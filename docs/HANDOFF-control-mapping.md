## 1. What this app is

Single-activity Jetpack Compose Android app, `com.example.cameraremotecontroller`,
minSdk 29 / targetSdk 37, AGP 9, arm64-only. It runs on a SIYI handheld ground
station (UniRC 10 Pro class) and displays several RTSP camera streams at low
latency.

The video stack is hand-written — libVLC was removed around 2026-09-10. Current
pipeline, one instance per camera panel:

- `RtspUdpPlayer.kt` — hand-rolled RTSP over TCP control socket + RTP over UDP
- `RtpH264Depacketizer.kt` / `RtpH265Depacketizer.kt` — RTP → Annex-B access units
- `LowLatencyVideoDecoder` (inside `RtspUdpPlayer`) — MediaCodec straight onto the Surface
- `GlVideoSurfaceView.kt` — GLSurfaceView + external OES texture
- `MainActivity.kt` (~75 KB) — all Compose UI

Measured end-to-end latency ~160–180 ms. See `LATENCY_MEASUREMENTS.md`.

**Conventions to respect:**

- `ktlint` runs with `ignoreFailures = false`. Lint failures break the build.
- Persistence is SharedPreferences with simple delimited lines — cameras are
  stored as `name|url|rotation`. Follow that pattern or use JSON, but keep it
  in SharedPreferences.
- Never drain decoder output on a free-running thread. Rotate views, never pixels.
  (These rules are about the video path — mentioned so you don't disturb them.)

## 2. The control-link finding

Full write-up: <https://claude.ai/artifact/3yAxjk9u9PZtnqA2GqBb1R>

The handset has **31 physical controls but only 16 communication channels.**
The limit is the S.Bus frame itself: 25 bytes, of which 22 are exactly
16 × 11 bits. There is no seventeenth proportional slot. The flags byte carries
two extra *digital* channels plus failsafe bits — no proportional data fits.
No firmware or UniGCS setting changes this.

**UniGCS is not the limiter.** Its Channel Settings (§4.2.4) and Button and Dial
Settings (§4.2.6) only decide *which* physical control lands in *which* of the
16 slots.

### The critical constraint for this work

**This app cannot remap those 16 channels.** The S.Bus stream is generated by
the SIYI ground unit firmware and configured by UniGCS, a separate app. There is
no public API for a third-party app to write UniGCS's channel map. Any mapper
UI built here drives *our own* control path, not the flight-control S.Bus.

### The three routes around the ceiling

1. **Six-position decode** — ArduPilot/PX4 read one channel as a 6-position
   switch, splitting 1000–2000 µs into bands, each firing a different
   `RCx_OPTION`. Six buttons collapse onto one slot. Parameter setup only.
2. **MAVLink over UART** — the air unit already runs MAVLink telemetry to the
   flight controller. Discrete actions belong in `MAV_CMD_DO_SET_SERVO` /
   `DO_SET_RELAY`. No channel cost.
3. **Ethernet straight to the payload** — the air unit has a LAN port
   (GH1.25 8-pin). Custom UDP protocol, any number of controls. **This is our
   route** — it is the only one this app owns end to end, and we already do
   custom UDP for the RTSP video path.

Deciding factor: flight controller → route 2, payload → route 3.

## 4. Task 1 — the probe (do this first)

**Question:** do the physical sticks, dials and switches reach *our* app as
Android input events, or does UniGCS grab them exclusively?

Everything downstream depends on the answer. The handset is an Android device,
so they may surface through the standard `InputDevice` API — or they may not
reach us at all.

**Build:** a small probe screen or a debug-only entry point. Enumerate input
devices, then log every event that arrives.

- Enumerate with `InputDevice.getDeviceIds()`, and for each device log the name,
  `sources` bitmask, and every axis in `motionRanges`
  (`MotionEvent.axisToString`).
- Override `onGenericMotionEvent` and log every axis value that changes.
- Override `onKeyDown` / `onKeyUp` and log every keycode.
- Surface the log on screen as well as Logcat — the handset may not be tethered
  during testing.

**Test procedure for the human:** move each stick (J1–J8), turn each dial
(LD, RD, LK, RK), flip each switch (SA–SF), press each button (L1–L3, R1–R3,
S1–S4, M1), squeeze each trigger (LS, RS). Record which produce events and
what identifier each maps to.

**Report back** with one of three outcomes:

- **A — sticks and switches both arrive.** Best case. Build the mapper on real
  hardware inputs.
- **B — only buttons arrive as key events.** Map those; use on-screen sliders
  for proportional payload controls.
- **C — nothing arrives.** UniGCS has an exclusive grab. The mapper drives
  on-screen controls only; hardware stays with UniGCS.

Also record, for whichever controls do arrive: are they still simultaneously
driving their S.Bus channel? A control that reaches us *and* moves the aircraft
cannot be safely reused for payload control.

### Probe implementation

Debug builds install a second launcher icon, **Input Probe**
(`app/src/debug/java/.../InputProbeActivity.kt`). It shows:

- every input device with its sources and axis ranges (re-enumerated on hotplug)
- a "seen" summary: each key/axis that produced an event, with count or min..max
- the 16 SIYI RC channel values from `SiyiRcChannelClient`, with channels that
  moved in the last 600 ms highlighted — this answers the "does it also drive
  its S.Bus channel" question in the same session
- a scrolling event log, mirrored to Logcat under tag `InputProbe`

`biz.siyi.remotecontrol` must be force-stopped for the channel panel to receive
data. Test twice: once with UniGCS stopped, once with it running, since an
exclusive grab may only happen while it is alive.

## 5. Task 2 — the mapper (only after Task 1 reports)

Do not start this until the outcome is known. The design below assumes A or B.

### Data model

A list of bindings, persisted as JSON in SharedPreferences:

- `sourceId` — hardware identifier from the probe (`J5`, `LD`, `SC`), or an
  on-screen control id
- `targetId` — payload function id
- `type` — proportional or discrete
- `min` / `max` — output range
- `reversed` — boolean
- `deadzone` — for proportional sources
- `enabled` — boolean

### UDP send path

New module, separate from the video path — do not entangle it with
`RtspUdpPlayer`. Sends control state to the payload over the air unit's LAN
port. Needs a defined wire format, a send rate for proportional controls
(discrete controls send on change), and a failsafe: what the payload does when
packets stop.

**Open question for the human:** the payload-side protocol is not specified
anywhere in the docs we have. Ask before inventing one.

### UI

Two columns — sources on the left, payload functions on the right — with
connections drawn between them, matching the sketch the user has. Ship the
simpler interaction first: tap a source, then tap a target. Drag-to-connect can
follow once the underlying binding model works.

Live value readout per binding is worth having early; it makes misconfiguration
obvious without a test flight.

## 6. Things not to do

- Do not attempt to write UniGCS's channel map. There is no API.
- Do not route payload controls through S.Bus. That is the constraint this
  whole document exists to work around.
- Do not touch the decoder threading or the GL rotation logic while adding
  this. Unrelated subsystem, hard-won behaviour.
- Do not assume a control is free to reuse just because it reaches Android —
  confirm it is not also driving an S.Bus channel.

## 7. LK/RK diagnosis and approved configuration — 2026-09-15

Live SDK command `0x48` returned the controller's actual output assignments:
CH8 was S1 (type 1, ID 0), CH15 was also S1, and CH16 was S2 (type 1, ID 1).
Neither LK nor RK was assigned to the 16-channel feed. Our app's saved CH8
label incorrectly said LK; its mapping screen only changes local labels.

The user approved CH8 = LK and CH16 = RK, retaining S1 on CH15. SDK command
`0x4A` acknowledged both writes (`[8, 1]` and `[16, 1]`). A CRC-validated
`0x48` read-back confirmed CH8 = type 0 / ID 8 and CH16 = type 0 / ID 9;
all other assignments matched the pre-change snapshot. S2 consequently no
longer has an output slot in this configuration. The installed app's saved
labels and the source default map were updated to match these two changes.

This evidence supersedes the earlier claim that no public channel-mapping
API exists: the SIYI UniRC 10 Pro manual documents read command `0x48` and
write command `0x4A`, and both worked on this device. These writes configure
controller output channels; they are separate from our app's local labels.

Configuration read-back is verified. Physical LK/RK movement in the app and
persistence across a controller reboot still require confirmation. The prior
raw capture had a steady 20 packets/second but no changes on any channel,
including the LD comparison, so it did not independently isolate knob motion.
